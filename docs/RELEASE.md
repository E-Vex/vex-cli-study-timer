# Release process

Releases are cut from `main` and packaged automatically by
[`.github/workflows/release.yml`](../.github/workflows/release.yml). When a
release is published, the workflow builds the Linux artifacts on GitHub's
x86_64 and arm64 runners and attaches them to the release page, so users can
download and run the timer without cloning or building anything.

## What gets built

Every published release receives the following assets, plus a `SHA256SUMS`
file covering all of them:

| Asset | Purpose |
| --- | --- |
| `vex-timer-<version>-linux-<arch>.tar.gz` | Portable archive: binary, `vex-timer(1)` manual page, `LICENSE`, and an `INSTALL.txt` with instructions |
| `vex-timer-<version>-linux-<arch>.AppImage` | Single-file executable; `chmod +x` and run on any distribution, nothing to install |
| `vex-timer_<version>_<debarch>.deb` | For Debian, Ubuntu, Mint, and other apt distributions |
| `vex-timer-<version>-1.<rpmarch>.rpm` | For Fedora, RHEL, openSUSE, and other rpm distributions |
| `vex-timer-<version>-linux-<arch>` | The bare statically linked binary for scripted downloads |
| `SHA256SUMS` | sha256 checksums of every artifact above |

`<arch>` is `x86_64` or `arm64`; `<debarch>` is `amd64` or `arm64`;
`<rpmarch>` is `x86_64` or `aarch64`.

All release binaries are **statically linked** (`-static`) and stripped, so
one binary per architecture runs on every Linux distribution — glibc or
musl-based, old or new — without any shared-library dependency. The packages
therefore ship no libc requirement either; the only optional runtime helpers
are `alsa-utils` (`aplay`, for sound) and `libnotify-bin` (`notify-send`, for
desktop notifications).

## Steps to cut a release

1. **Bump the version** in `src/version.h` so `vex-timer --version` reports
   the version being released.
2. **Update `CHANGELOG.md`**: move the `[Unreleased]` entries under a new
   `## [<version>] - <date>` heading and add the matching link definition.
3. **Commit**, for example `chore: release 1.5.0`.
4. **Tag and push**: `git tag vX.Y.Z && git push origin vX.Y.Z`.
5. **Publish the release**, either through the GitHub UI or with:

   ```bash
   gh release create vX.Y.Z --title vX.Y.Z --generate-notes
   ```

6. **Watch the "Release" workflow run** in the Actions tab. The
   `linux / x86_64` and `linux / arm64` jobs build in parallel, and the
   `attach artifacts to release` job uploads everything to the release page.

The workflow fails on purpose if `src/version.h` does not match the release
tag (e.g. tag `v1.5.0` requires `#define VEX_VERSION "1.5.0"`), because
mismatched names would confuse the packages and the download page. Fix the
header, delete the release (or re-tag), and publish again.

## Testing the pipeline without cutting a release

Run the workflow manually from the Actions tab, or:

```bash
# Build both architectures only; artifacts stay in the workflow run.
gh workflow run release.yml

# Build and attach artifacts to an existing release, e.g. to backfill it.
gh workflow run release.yml -f tag=vX.Y.Z
```

On a manual run the version check only warns instead of failing, and without
a `tag` input the `publish` job skips uploading entirely.

## Notes

- The workflow only ever adds or refreshes its own assets via
  `gh release upload --clobber`. Source archives (auto-generated by GitHub)
  and any assets uploaded by hand stay untouched.
- The workflow checks out the tagged commit for the source it builds, and
  the commit that launched the run for the packaging templates under
  `packaging/`. Template changes on `main` therefore apply immediately —
  including when an older release is re-uploaded with `workflow_dispatch`.
- The packaging metadata lives in `packaging/`: the AppImage `AppRun`,
  desktop entry, and icon; the deb control and copyright files; the rpm spec
  template; and the tarball's `INSTALL.txt` template. Edit there, not in the
  workflow, when changing package metadata.
- `make install DESTDIR=... PREFIX=/usr` is the single source of the staged
  file layout, so the packages, the tarball, and a manual install all place
  files identically.
